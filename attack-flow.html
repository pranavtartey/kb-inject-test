Security finding — kb-inject

How the kb-inject attack reached Kuberns

One attacker (fake identity, disposable email) tried two separate delivery paths into the same Kuberns deployment pipeline. Both land the malicious container on the agent's own EC2 box, next to the agent's real backend — then it probes for secrets in four directions at once.

Kuberns' own infrastructure attacker-controlled / attack path
Two entry paths, one target. GitHub with a leaked token, or a self-hosted git server — either way the payload ends up running next to the agent's own backend.
No isolation between neighbors. The deployed app and the agent's backend/docker-gateway share one EC2 box, so one compromised container can reach the others.
Four probes fired at once. Read the agent's own .env, try to prompt-inject the agent via CLAUDE.md/AGENTS.md, scan for an exposed Docker API, and query AWS IMDS for IAM credentials — then ship it all out over a Cloudflare tunnel.
